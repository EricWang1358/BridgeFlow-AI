# 17 — 业务用例设计 MVP 的验收与演示

> 演示范围与未完成项以 [链路审计](19-chain-audit.md) 和 [最新状态](00-status.md) 为准。
> 正常案例可以展示；「人工意见禁止重跑」、完整超时与重启恢复尚未收尾，
> 所以下面这份流程说明不等于稳定 MVP 的全项验收。

这一篇解决两个问题：现在能向业务用例设计负责人演示到什么程度，以及怎么自己复演一遍。
能演示的是「导入 → 规则计算 → 部门独立研判 → 人工决定 → 可重开报告」这条工作方式。
数据是透明生成的制造企业案例，验收针对这条月度闭环，不等于真实企业上线、正式财务报表签发，
也不等于 rubric 全项满分。实测结果、时延、调用量与证据统一在 [00](00-status.md) 的「各轮验收记录」。

## 验收口径与各部门的责任

这一轮的审查人是开发代理模拟的业务负责人，核对的是可复算结果、部门权限与模型原文，
没有冒充真实部门负责人签字。业务方仍要确认自己的字典、单据粒度、成本符号、币种、信用规则与成功判据。

| 部门 | 应交付的判断 | 计算依据 | 谁定下一步 | 不能越过的边界 |
| --- | --- | --- | --- | --- |
| 生产 | 工时负荷、剩余工时 | 声明的实际工时与可用工时 | 运营负责人 | 分析员不批准加班预算、不承诺客户交期；每条班次的可用工时只能登记一次 |
| 采购 | 实际支出、同数量预算价格偏差 | 逐行单价乘数量再求和；不能把单价相加当支出 | 采购负责人，涉及预算时联同财务 | 不改销售报价；缺价、缺量或币种不符时拒绝计算 |
| 财务 | 项目毛利、余额加权账期 | 收入与正数成本独立列示，应收余额作权重 | 财务负责人 | 不把净发生额称作收入；不能从毛利或平均账期推断减值、坏账或信用趋势 |
| 市场 | 同期订单与产出差额、数量加权请求账期 | 总量比较与声明权重 | 销售负责人，信用条件交财务审批 | 总量充足不等于品项齐套；不生成客户 Tier、价格带或自动承诺账期 |
| 协调者 | 汇集有效判断，列出责任与未完成部门 | 官方子会话结果与后端校验 | 业务负责人协调，人来裁决冲突 | 不把部分失败写成成功；不执行采购、排产、报价或授信 |

`risk` 场景触发声明的关注条件，`balanced` 回到正常范围。标准答案在
[expected.json](../data/business_demo/expected.json)，由生成器独立显式算术产生：应用的公式求值器不参与生成答案，
模型也拿不到答案文件。这一组是可见的开发与演示集，不是留出评测集；本 sprint 没有读 `data/acceptance/`。

界面入口见 [demo-walkthrough](../demo-walkthrough/README.md)，页签与轻量文件栏的设计取舍见
[18](18-native-captain-and-state.md)。

## 演示准备

在仓库根目录，先按 [HANDOFF](../HANDOFF.md) 装好锁定的 Python 与 DSH npm 依赖。
演示请用独立目录，免得把合成映射写进你自己的业务记忆：

```bash
source ../.venv/bin/activate
source ./env.sh
python scripts/make_business_case.py
export DSH_HOME="$(mktemp -d /tmp/bridgeflow-demo-dsh-XXXXXX)"
export RESULT_STORE_PATH="$DSH_HOME/business-output"
export MAPPING_MEMORY_PATH="$DSH_HOME/mappings.json"
export FIELD_DICTIONARY_PATH="$PWD/data/business_demo/dictionary.yaml"
pnpm --dir plugins run build
python scripts/start_web.py --port 3082
```

打开启动器打印的认证地址。这里用默认原生 Web，不启用 `/console`。导入不调模型；
在聊天里提交请求会用 shell 配置的真实模型。

### 先决条件：字典必须是本案例那一份

这一步不做，下面第 2 步一定走不通。本案例只在自己的字典下成立：
`data/business_demo/dictionary.yaml` 是唯一声明了 finance 可连接列（`project`）和 `business_review`
契约的字典。默认的 `data/mappings/field-dictionary.yaml` 两样都没有，于是导入会成功、批次回
`needs_configuration`、`review_context` 拒绝：第 1 步过，第 2 步不可能。实测过一次，就是这么坏的。

```bash
source env.sh && python3 scripts/start_web.py --demo --port 3082
```

`--demo` 把服务指向本案例的字典，启动时会打印 `BridgeFlow field dictionary: …`。
面板上「为什么主表是空的」下面也会显示本批次冻结的是哪一份字典，对不上就是这里对不上。

字典从哪来这件事本身也有答案了：**模型起草，人逐条审核，发布才生效**（2026-09-18 业务负责人对
2026-09-07 边界的修订，#205；需求见 [E05-UC07/UC08](requirements/05-mapping.md)，尚未实现）。
现阶段演示用的仍是既定案例里那份示例字典——它是例子，不是「客户必须先手写一份」的前提。
无论字典从哪来，匹配的候选集始终只能来自已声明字段并附证据，见 [`../CLAUDE.md`](../CLAUDE.md)。

## 台上怎么操作

1. 在左侧「来源」栏点「＋ 添加来源」，导入 `data/business_demo/risk/` 下各部门 CSV（导入后四份文件列在来源栏里，点开即预览），
   业务月份填 **2025-11**（与[案例说明](../data/business_demo/README.md)一致）。
   讲清楚待确认映射与隔离行的区别：未确认的映射不会被本次汇总直接消费。
2. 点「发起研判」，请求直接进当前会话，不用复制粘贴（想先改一句就用旁边的「改一改再发」）。
   观察 `review_context → 同一响应四次 subagent → review_finalize`、轨迹里的四次 Spawn、顶栏四个子代理。
   每个部门都有自己的会话编号与结构化结果。
3. 点「对话｜轨迹」右边的「业务状态」页签，打开「四部门报告」，看部门负责人、风险方向与建议。
   公式直接显示；展开一项「解释与原始来源」，沿文件、原始行号、原始列名核对。
   来源展示封顶只是展示层，不代表只用样本算数。
4. 在同一环境导入 `balanced/` 作为新批次，再研判一次。比较风险方向，并重开旧批次，确认它没有被覆写。
   别说「回到正常范围就等于所有风险消失」。
5. 演示映射审批时说清楚两件事：工具参数里的 `accepted=false` 是「记录一项否定关系的决定」，
   仍然需要批准才写入；审批面板里的「拒绝」是不执行这次写入。两者不能混称。
6. 在会话里要求对指定合成关系调用一次 `confirm_mapping`，填一条可选的拒绝理由后拒绝。
   模型应当解释未写入并转述理由，并说明未来导入仍可能询问。批准才会记录进记忆。
   审批日志与记忆文件的结果由自动复测验过。

隔离修复的演示用源文件副本：把日期改成歧义格式，导入后报告应拒绝；修正源文件再导入新批次来恢复。
现在没有隔离 release/discard，也没有字段映射向导，不要在台上假装这些按钮存在。

## 自动复演

```bash
# 不调用付费模型：完整原生浏览器与故障路径
cd plugins
pnpm run smoke:web
pnpm run smoke:business
BRIDGEFLOW_CASE=balanced pnpm run smoke:business
BRIDGEFLOW_TEST_FAULT=step-limit pnpm run smoke:business

# 真实模型：先在仓库根 source env.sh
BRIDGEFLOW_LIVE=1 pnpm run smoke:business
BRIDGEFLOW_LIVE=1 BRIDGEFLOW_CASE=balanced pnpm run smoke:business
BRIDGEFLOW_LIVE=1 pnpm run smoke:web
```

每次脚本都创建临时 DSH_HOME、私有服务凭证、批次输出与映射记忆，并关掉自己启动的服务。
终端会输出证据目录。业务测试保存报告、截图、测量 JSON 与原生 JSONL；审批测试保存成对的决定、
拒绝备注与实际模型叙述。真实模型跑的输出没有经过离线适配器替换。

失败路径覆盖：缺价、币种不符、符号不符、零分母、歧义日期、重复行交易身份不明，
以及模型篡改数值 / 单位 / 状态 / 动作、讨论被明确禁止的财务命题。子会话连续输出无效结构时触发步骤上限，
整单标 `partial`，那个部门不补伪造的判断。partial 页面可以向原队长提交人工复核意见，
系统不替缺失部门签字，也不强制重跑整组。

## 这一轮发现并修掉的问题

- 官方审批的默认呈现只有决定枚举，没有备注字段。改为通过官方 `conversation.composer` slot 加映射专用输入，
  仍然调用官方 `pending.answer`，不修改官方审批服务、不 fork DSH。备注先走同源鉴权与
  「当前会话 + 调用」绑定的临时票据，再进入原生会话审计与既有拒绝反馈。备注不授予写权限。
- `list_metrics` 的 Python 返回里带着内部计算配置，而 TS 公共输出禁止额外字段。工具壳现在显式投影公共字段；
  浏览器测试在真实派发中执行目录与聚合，正常用例里禁止隐藏的工具错误。
- 拒绝反馈的原文只说「不记住」，真实模型据此说过「下月不再询问」。现在明确写「未来仍可能询问」，
  真实模型复测会核对叙述与文件。
- 正毛利曾被真实模型扩写成「无需计提损失」。收紧了解释任务，并对字典声明的禁止命题执行校验；
  不把规则通过当作开放文本语义正确的完整证明。
- 旧去重会删除相同内容行。业务总额在出现这种修正时直接拒绝，要求先核实交易身份；
  原始行号在去空、去重、隔离之后仍可追溯。

## 还差什么

业务用例设计演示可以开展。要进真实企业试用，还缺：真实 OA 字典与脱敏单据验收、员工身份与角色/租户边界、
字段配置与隔离处置、版本差异与签发流程。平均指标可能掩盖单个客户的风险；当前没有客户级信用规则、
库存 / BOM 齐套模型或动态报价依据。普通聊天里的叙述是模型的解释，正式数值与权限结论以报告的校验字段为准，
不能把它直接签发成财务报表。

远端看板建议见 [16](16-dsh-web-review.md)：把本地证据用于评审，不要用卡片数量或「用了哪个 DSH 包」
换算 rubric 完成度。本轮没有修改远端 issue 与看板。
