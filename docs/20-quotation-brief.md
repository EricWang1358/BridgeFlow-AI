# 20 — 报价功能任务书

> 读者是接手实现这个功能的人（或 agent）。语言：中文，内部工程记录；代码、注释、commit message、
> issue 标题用英文。

## 一 这是什么，不是什么

这是一个并列的功能，不是方向转变。四部门月度对账继续存在，报价是它旁边的第二条路径，
不要为了做这个去拆现有管线。

业务方原话（2026-09-07）：

> 这个得要结合一个具体的应用场景，你先从简单的来吧。
> **从客户会话和采购反馈的采购合同作为输入，输出报价单。就先只涉及两个部门。**
> 我到时候会把样板案例上传。

| 维度 | 四部门对账（已有） | 报价（本任务） |
| --- | --- | --- |
| 输入 | 四份同期部门表 | 客户会话记录 + 采购合同 |
| 部门数 | 4 | 2 |
| 主对象 | Master Table | 一张报价单 |
| 时间轴 | 月度、跨月可比 | 单次交易 |
| 产出 | 发现 / 张力 / 卡片 | 可外发的报价 |

## 三 三条最容易踩的硬约束

### 1. 原始数据行不进上下文，但文本输入要重新划边界

现有这条约束是为 20 万行明细写的：模型拿的是计数、公式和封顶的证据样本，不是行。

报价场景第一次引入自由文本（客户会话记录、合同条款），这里既不能机械套用，也不能就此放弃：

- 一份合同的付款条款、数量、单价、交期必须被读懂才能报价，这跟 20 万行明细不是一回事。
- 但把整份文件灌进上下文同样不可接受：不可审计、不可复现，而且体积随文件大小无界增长。

要求：先做结构化抽取，再让模型在结构化结果上推理。抽出来的每一项都要带出处（文件、页或段、原文片段），
沿用 `SourceRef` 的形状。模型看到的是抽取结果加出处，不是整份文件。抽取失败就拒绝并说明原因，不许猜。

这是本任务最重要的设计决定，先把它写清楚，再写代码。

### 2. 字段名不写进代码；匹配的候选集只能来自已声明字段

标准格式由人声明；初始字典的起草已于 2026-09-18 改为「模型起草 + 人逐条审核发布」
（#205，见 [CLAUDE.md](../CLAUDE.md) 同名小节与 [E05-UC07/UC08](requirements/05-mapping.md)），
但对报价这条链路没有变化：模型的职责仍是把上传件的列或字段匹配到**已声明**的字段，候选集是封闭的。
不要写任何形如「如果这一列叫 price 就是单价」的代码。

报价单本身的标准格式也要由人声明，与 `business_review` 契约同构。可以对照
`data/business_demo/dictionary.yaml` 的 `business_review:` 段，以及
`backend/src/bridgeflow/business.py` 是怎么按声明求值的。

### 3. 结论带证据，拒绝优先于猜测

报价单上的每一个数字都要能追回到某份输入的某一处。算不出来就拒绝出数，并说明缺什么。
这是本产品的核心叙事，而且它在对外报价上比在内部研判上更要紧：内部看错了还有人复核，
外发出去的就是对客户的承诺。

## 五 分三步，第一步现在就能做

### 第一步：把「报价单」变成一份声明，而不是一段代码

样板案例到手之前就可以做。做完的验收是：一份声明加一组合成输入，能产出一张带出处的报价单，
或者一条点名缺什么的拒绝。全程不调模型。

1. 在字段字典里设计 `quotation:` 契约段，与 `business_review:` 同构：报价单有哪些字段、
   每个字段由哪个表达式算出、阈值是什么、谁是决策负责人。
2. `business.py` 的 `expression()` 已经能按声明求值并收集 `SourceRef`。确认它够不够用，不够就扩展，
   但不要为报价单写一条专用代码路径。
3. 写出拒绝的形状：缺成本、缺产能、缺付款历史时，报价单拒绝出数并点名缺什么。
4. 单元测试用合成输入，不要等样板。

实现入口：文本抽取与证据边界先写在 [设计记录](21-quotation-design.md)；人工维护的合成声明在
[`data/quotation_demo/dictionary.yaml`](../data/quotation_demo/dictionary.yaml)，通用执行入口是
`bridgeflow.documents.evaluate_document`，算术仍由 `business.expression` 执行；合成验证见
`backend/tests/test_declared_documents.py`。结果与费用记在 [实测状态](00-status.md)。

那份示例字典只用于隔离验证。部署时由管理员把确认后的 quotation 段并入现有字段字典，
保留月度路径需要的声明，不要用只含报价示例的文件覆盖月度字典。报价页通过已鉴权的只读契约接口
展示当前配置。原生 Web 的「报价工作区」入口在空会话也可用，在右侧 Studio 打开声明与所需依据的预览：
左侧 Sources 只列实际上传的来源，中间保留原生会话，Studio 工具区下方只列已保存产物，
不冒充已抽取的文件或已生成的交易报价。这里没有开放原件解析、未经验证的事实写入或报价外发入口。

### 第二步：样板案例到手之后

先回答四个问题，并把答案写回本文件，再动代码：

- 两份输入各是什么格式？会话记录是纯文本还是已经结构化？
- 报价单的标准格式是什么？字段由谁声明？
- 每个数字要追回到哪份输入的哪一处？
- 两个部门分别是谁，决策负责人是谁？

然后实现第三节第 1 条的结构化抽取（带出处、可拒绝），并把抽取结果接到第一步的声明上。
在答案落地之前不要猜输入格式并据此写解析代码。

### 第三步：人在环内

报价外发之前必须经人批准，复用现有审批闸门，不要新建一套。拒绝要带理由并回到会话，
模型必须如实转述，不得声称已发出。

## 六 不要做的事

- 不要为了这个功能改动或删除四部门对账路径。
- 不要在样板案例到手前猜测输入格式并据此写解析代码。
- 不要把整份合同或会话记录塞进模型上下文。
- 不要让模型产出字典条目，或断言价格带。
- 不要新建第二套审批、第二套证据结构、第二个前端。
- 不要扩大范围：Docker、CI、自建前端都被明确排除过。
