# 26 — 与 ERP 定制化的对比：我们解决什么、不解决什么（#119）

> 参考文档，给写 proposal / PPT 的人用。每条「我们的做法」都指向已合并的代码或测试，
> 不写尚未实现的能力。数字只在 [`00`](00-status.md)。

## 结论先行

BridgeFlow 不是 ERP 的替代品，而是 **ERP 定制化之前、之外的那一段**：公司还没有（或不打算上）ERP 时，
把散在部门表格里的数据按人批准的标准对齐、补齐、交接，并把「标准是什么」变成可审批、可版本化的声明。
ERP 定制的三个痛点——周期长、偏离需求、信任成本高——根源都在「需求要先翻译成代码」。
我们把这一步换成「需求写成声明，人批准后立即生效」，代码只负责执行声明、拒绝猜测。

## 三个痛点逐条对比

### 1. 交付周期长

| | 典型 ERP 定制 | BridgeFlow |
| --- | --- | --- |
| 改一个字段口径 | 提需求 → 开发改表结构与报表 → 测试 → 发版 | 改字典 YAML，下一次导入即生效；旧批次冻结不重算 |
| 部门表头叫法不同 | 统一模板、培训员工按模板录入 | 模型只在已声明字段中提议匹配，人审批一次，之后自动沿用（`column_matches.py`，#146） |
| 新增一个交接环节 | 定制流程引擎 | 在工作流目录里声明阶段、输入输出与负责角色（`data/workflow_demo/catalogue.yaml`，#149） |

代价：声明需要有人写、有人批。没有字典负责人，系统就停在「未配置」，不会自己补上。

### 2. 定制质量无法保证、偏离需求

| | 典型 ERP 定制 | BridgeFlow |
| --- | --- | --- |
| 需求在代码里的样子 | 分散在表结构、存储过程、报表逻辑中，业务方读不懂 | 集中在声明文件：字段、单位、公式、阈值、责任人，业务方可读可批 |
| 数值从哪来 | 报表层计算，出错难追 | 确定性代码按声明公式计算，每个数字带回源文件、工作表、行、列（`SourceRef` 在 schema 层强制） |
| 模型会不会编 | 不适用 | 部门结论由 `validate_role` 按可信事实重建，数值、单位、状态或动作被替换即拒绝（`test_business_mvp.py`） |
| 需求没说清时 | 开发按理解实现，上线后才发现偏差 | 缺失、歧义、冲突一律变成问题或隔离，不填默认值（`workflow/intake.py`、`quarantine.py`） |

业务代码里不写任何字段名，由测试解析源码强制（`test_no_field_name_is_written_into_the_module` 等）。
这意味着换一家公司、换一套表头，改的是声明，不是代码。

### 3. 信任：业务信息要交给外部开发

| | 典型 ERP 定制 | BridgeFlow |
| --- | --- | --- |
| 原始数据给谁看 | 实施方需要拿到大量真实数据调试 | 原始数据行不进模型上下文；模型只拿统计、哈希重合度与引用（`CLAUDE.md` 硬约束，工具返回值有上限） |
| 谁能改数据 | 系统管理员 | 每次写入都要当事人在审批卡上确认，回执与请求逐字节绑定、一次性（`security.consume_approval`） |
| 出了问题怎么查 | 查日志、问实施方 | 事件日志回放出每个状态；审批决定、拒绝理由、隔离处置、映射依据都落盘可审计 |
| 被注入怎么办 | 不适用 | 表格里的指令式文字在真实派发处被拒，后端请求 0 次（攻击用例逐工具跑，`runtime.test.ts`） |

## 从 ERP 设计里值得借鉴、我们还没做的

诚实列出，排序按对本项目的价值：

1. **主数据管理。** ERP 有统一的客户、物料、项目主数据；我们靠字典声明加跨部门值重合找对应关系，
   同一实体在不同部门的编码仍需人确认。长期看需要一张被批准的主数据表，而不是每批次重新对齐。
2. **期间关账。** ERP 有明确的会计期间与关账动作；我们有冻结批次与派生批次，但没有「本期已关、不再接受修订」的状态。
3. **权限与职责分离。** ERP 按角色控制谁能录入、谁能审批；我们目前只有「经认证会话 + 每次审批」，
   员工身份与角色按 [`24`](24-meeting-2026-09-13.md) 的决定作为远景，交给接入的平台。
4. **与外部系统的双向集成。** ERP 通常直连银行、税务、供应商门户；我们只有本地入库适配器与待接的飞书上传下载（#140）。
5. **规模。** 工作流事件回放是全量的，适合演示规模；数据量上来需要物化投影（记在 [`25`](25-workflow-foundation.md)）。

## 讲给评委时的一句话

> 传统 ERP 把业务规则写进代码，所以改规则就是改系统；我们把规则写成人能读、能批的声明，
> 让 Agent 只做「在已批准的规则里补问、匹配、解释」，每个数字都能追回单元格，每次写入都要人确认。
