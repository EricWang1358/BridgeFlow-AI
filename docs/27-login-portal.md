# 27 — 统一登录门户与飞书 RBAC

需求规格要求 RBAC：控制每个登录用户可以访问的数据源。2026-09-13 定的做法是**解耦**：
一个统一登录门户，可接入多种应用；第一个身份方案是飞书，第一个接入的应用是 BridgeFlow。

这篇只记决策与理由。实测数字在 [`00`](00-status.md)，当前进度在 [`../HANDOFF.md`](../HANDOFF.md)。

## 架构

```
浏览器 ──► dsh web（/bridgeflow 代理）──► BridgeFlow backend
   │         转发 X-Portal-Token                 │ 用 JWKS 验签
   └─ 飞书 OAuth ──► 门户 portal/ ── JWKS 公钥 ──┘
```

- **门户（`portal/`）**：独立进程。飞书网页登录（授权码流程）证明用户身份，换取
  union_id / name / email；凭门户会话 Cookie 签发短期应用 JWT（Ed25519，15 分钟，
  `aud` 按应用区分）。公钥从 `/.well-known/jwks.json` 发布。无数据库：会话是签名
  Cookie，应用令牌是短期 JWT，全部无状态。
- **应用（backend）**：只持有门户公钥，本地验签，不碰飞书凭据、不维护登录态。
- **插件（dsh web）**：`web.ts` 代理在既有 DSH 会话栅栏之上**叠加**转发用户令牌；
  401 时客户端向门户换一次令牌重试一次，仍不行就弹「飞书登录」入口。

## 为什么是 JWT + JWKS，而不是门户代验

应用每次请求都去问门户「这令牌是谁」，门户就成了所有应用的单点与热点。签名令牌把
信任锚点收敛到一个私钥：门户私钥绝不出库、绝不进上下文（`PORTAL_KEY_PATH` 由启动
shell export，与 `DSH_*` 同一条边界），应用只需要公钥。撤销靠 15 分钟过期，不靠在线
查验——本期没有踢人需求，真有了再加黑名单。

## 为什么权限映射应用自持，但成员关系不自持（2026-09-18，#204）

门户只管「你是谁」。「张三能看财务部的表」曾经也是 BridgeFlow 自抄的一份逐人花名册
（`access-control.yaml` 以 union_id 为键逐人登记）——会腐烂、每个新客户部署都要维护、
与飞书通讯录双重事实来源。2026-09-18 评审确认后拆分：

- **成员关系以飞书为唯一事实来源**：每个业务部门与总经理办公室各对应一个飞书知识库，
  运行时以 tenant token 查 `wiki/v2/spaces/{id}/members`（5 分钟缓存），库里是 member
  还是 admin 决定角色。入离调岗在飞书生效后（缓存过期内除外）自动跟随，BridgeFlow
  零改动。
- **BridgeFlow 只自持「角色 → 操作」业务规则**：`access-control.yaml` 瘦身为
  「结构映射 + 角色策略」——哪个知识库代表哪个单位（`spaces`）、每个角色能看哪些部门、
  能做哪些操作（`roles`）。这是飞书表达不了的业务判断，仍由人预设，改 YAML 不改代码。

wiki 成员接口返回 open_id，与登录用的 union_id 不同源；桥是门户 JWT 里早已携带的
`open_id` claim，后端验签时记录观察到的 union_id ↔ open_id 对。

三条不变：

- 未在任何知识库里的用户看到空集 = 看不到任何批次；
- 结构映射缺失或非法 = 503「未配置」，绝不退回猜测；
- 飞书不可达 = 503，绝不退回过期缓存或静默空集。

前置条件（飞书管理后台，人工一次）：应用加 `wiki:member:retrieve` 权限并发版
（tenant token 调用，发版即生效，无需全员重登）；把应用本体加为每个知识库的成员，
否则查询被拒。群组/部门型成员不会被展开——授权以「人直接加进知识库」为准。

这与字段字典（`data/mappings/field-dictionary.yaml`）仍是同一条约定：改 YAML，不改代码。

## 控制台门禁：进得去也是一项授权（2026-09-20，#229）

`forward_auth` 原先只问「这个浏览器有没有登录会话」，于是任何已登录员工都能到达代理控制台，
哪怕他在 ACL 里一项 `operations` 都没有。而控制台是**共用的一个 dsh 身份**：进去的人彼此的会话、
笔记本与待审批互相可见。所以「进得去」现在是一项被声明的操作 `console_access`，省略即无权。

判定不在门户重写：门户 `/verify` 用自己刚签的用户令牌问后端 `/identity/console-access`，
后端按 JWKS 验签后走既有 `access_resolver`，角色规则仍只在 `access-control.yaml` 一处。
`/identity/console-access` 是唯一不挂 `require_host` 的路由——门户不持有宿主凭证，也不该持有：
那把令牌是模型运行时的，交给身份服务等于把信任方向反过来。

三种结局，措辞必须分得开：

| 情形 | 状态码 | 说明 |
| --- | --- | --- |
| 有 `console_access` | 200 | 放行 |
| 已登录、无该授权 | 403 | 确定的拒绝；重新登录修不好，所以页面不提供「重新登录」 |
| 授权无法确认（应用不可达、ACL 缺失、飞书不可达） | 503 | 扣下不等于拒绝，页面明说「这不是拒绝」 |

503 扣下的是整站而不只是控制台，这是有意的：`forward_auth` 后面只有 dsh web 一个站点
（[`22`](22-lightsail-deploy.md) §7），四部门浏览页也在这个 shell 里，没有另一个只读站会因此被牵连。

门禁**默认关闭**：未设 `PORTAL_CONSOLE_CHECK_URL` 时 `/verify` 行为与从前相同。开启是部署步骤，
因为没人声明过这项授权时打开它会把所有人锁在门外。答案缓存 60 秒，失败不缓存——一次故障不该粘在会话上。

这一步不是按人隔离：控制台仍然共用，同时在里面的人互相可见。按人隔离已按
[`35`](35-seat-isolation.md) 落地为席位方案，见下节。

## 席位认领与子域名绑定（2026-09-20，docs/35；同日改为先到先得）

按人隔离的形态是**固定容量的通用席位**（一人一个 dsh 实例），先到先得认领——配置文件里
不出现任何人名。门户两处行为随 `PORTAL_SEATS_PATH`（容量声明 `data/mappings/seats.yaml`）、
`PORTAL_SEAT_BASE_DOMAIN`、`PORTAL_SEAT_ASSIGNMENTS`（认领状态 `data/seats-assigned.json`，
untracked 实例状态）开启；未配置时门户行为与从前完全相同：

- **`/enter` 认领或复用**：已有认领 → 交接到自己席位 `https://<seat>.console.<domain>/`
  并带该席位 home 的 launch token；无认领 → 先过 `console_access` 门禁（无授权者不消耗
  容量），通过即认领第一个空位；满员 → 403「席位已满」。认领文件逐请求重读，运维释放
  即时生效、无需重启门户。
- **`/verify` 的席位绑定校验**（在门禁之前、且独立于门禁）：请求 Host 的席位认领人 ==
  登录人才放行；他人席位与**未认领席位**一律 403。这是路由层事实，门禁关闭的部署上它
  同样成立。Caddy `forward_auth` 保留原始 Host（备用读 `X-Forwarded-Host`）。
- `/health` 上报 `"seats": <容量>` 与 `"seats_assigned": <认领数>`，preflight 据此核对
  两份文件与运行态一致。

角色事实不因先到先得而变：**能否认领**仍由 `access-control.yaml` 的 `console_access`
决定（#229），先到先得只在获授权者之间进行；腾出席位是显式运维动作
（`provision_seat.sh --release`，home 归档不丢数据）。飞书与 Lark 的 `union_id` 不同源，
同一个人在两个平台就是两个主体、可各自认领——拍板记录在 [`35`](35-seat-isolation.md) §0。

## 可见性规则（本期粒度：按部门过滤批次）

批次可见 ⟺ 批次的部门集合 ⊆ 用户授权部门，或该用户是导入人（`BatchSnapshot.owner`）。
不可见返回 **404** 而不是 403——批次是否存在本身就是信息。上传侧对称：只能上传自己
有权看的部门。存量批次 owner 为空，天然 fail-closed，无需迁移。

模型只读工具的**授权**仍是可信主机身份；**归属**自 #231 起由浏览器交出的门户令牌承担（见下节），
两者不要混为一谈。批准写入另要求员工授权许可及原生审批，见后文；这不等于原生会话和模型读取已完成个人隔离。

## 飞书侧需要开通什么

复用 #140 的自建应用即可（凭据同一对，权限范围不同）：

1. 「网页应用」能力，回调地址配置为 `$PORTAL_EXTERNAL_BASE_URL/callback`；
2. 获取用户 user_id 的通讯录只读权限（否则 user_info 没有 union_id，门户会报错而不是猜）；
3. `wiki:member:retrieve` 并发版（角色解析用，tenant token；应用本体须加为各知识库成员，见上节）。

Drive 快捷调用（tenant token）与登录（user token）互不依赖：一个配了另一个不配，
各自报各自的「未配置」。

## 明确不做（本期）

管理员控制台、门户侧用户管理 UI、多身份提供商（apps.yaml 的结构为此预留），以及原生会话/读取的完整员工隔离。操作权限和批准回执的个人绑定已实现如下。

## 浏览器总表及工作流范围补齐（2026-09-16）

总表 JSON 与 XLSX 下载现在同样要求门户身份，并在读取原件/生成工作簿前执行批次可见性检查。工作流浏览器视图另用访问配置中的 `workflow_departments` 精确名称列表；导入部门 ID 与工作流业务名称不自动互相推导。

未授权的模板、阶段、血缘和看板行不出现在列表；交接阶段必须覆盖该阶段及所有输入输出模板的部门范围。草稿直接访问返回 404。采用信号按部门/阶段过滤，全局通知故障只对覆盖全部目录的人显示。没有工作流授权的用户看到空列表；省略新配置不扩大旧权限。

共享主机读取工具仍是可信边界，不能将其暴露为浏览器通用代理；它的调用现在能归属到人（#231），
但归属不是授权。批准写入的员工授权见下节。

## 模型发起的读取归属到人（2026-09-20，#231）

`BRIDGEFLOW_SERVICE_TOKEN` 退回它该干的事：**传输凭证**，证明调用来自宿主进程。身份不再由它承担。

模型发起的工具调用背后没有浏览器，所以以前它到后端时只有宿主凭证，审计能证明「发生了一次读取」，
证明不了「是谁的那一轮导致的」。做法不是让宿主**断言**一个名字——宿主断言身份和从前是同一种信任，
只是加了个标签。改成浏览器把自己手上的门户令牌交出来：宿主先让后端 `/identity/me` 验签一次才肯存，
此后模型触发的读取原样转发这个令牌，后端**逐请求验签**，与浏览器调用走的是同一条 `require_user`。

两条刻意的限制：

- **有歧义就等于没有**。绑定按会话记，但工具的 `exec` 只有 `callId`／`rootCallId`／`agent`，没有会话 id。
  当前只有一个人绑定时，这一轮就属于他；同时有两个人绑定时，挂上任一个都会把 A 的运行记到 B 名下——
  错的名字比没有名字更糟，所以什么都不挂，审计照旧记成主机读取。
- **过期是真过期**。门户令牌约 15 分钟。过期的绑定直接丢掉而不是转发一个后端本来就会拒的令牌；
  无人值守的长任务因此退化为「无归属」，不会伪造归属。

审计里三种主体从此分得开：`user:<摘要>`（验签到人）、`host`（无归属的主机读取，也就是 #231 之前
每一次模型调用的样子）、`anonymous`（无调用者）。审批备注的 `author` 同理：有绑定时记人，
没有时仍记 `dsh-authenticated-session`——那句字面意思就是「共用 dsh 会话里的某人」，如实即可。

**这一步没有做**：把「无归属」变成拒绝。模型读取的授权仍是主机级，缺少归属时读取照样执行。
把它改成 fail-closed 是另一次拍板（需要考虑无人值守运行与演示），不在本步范围。

## 员工操作与原生批准（2026-09-16）

ACL 的 `operations`（现在挂在角色上，#204）省略为空集；查看权限不隐含上传、备注或批准权限。配置见 `data/mappings/access-control.yaml`（跟踪在仓库里，随部署下发；见 docs/22 §5b）。上传使用 `batch_import`，备注使用 `review_note`；批准写入使用工具名称作为操作名。

浏览器 `/bridgeflow/approval-authorize` 只接受活动原生审批的会话、调用与票据；准确操作/请求体由主机取得，浏览器不能替换。后端 `/identity/authorize-write` 同时要求主机认证和员工 JWT，再检查操作及数据范围。许可短期有效、精确内容绑定、一次使用，仅留在主机内存。原生 Allow 后才签发带许可的回执；后端消费时重新核对 ACL，模型填写的姓名不参与身份判定。

审计表 `employee_authorizations` 保存员工、操作、请求摘要和调用，但仅证明授权被消费，不证明后续业务成功。拒绝/取消记录仍为共享会话，原生会话、审批查看及模型只读工具没有完整员工隔离；部署不能以这次写入保护宣称多租户安全。真实飞书联调仍需配置与验收。
