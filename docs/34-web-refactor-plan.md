2026-09-20。形态决策与完整取舍论证见 issue #227，本篇是它的落地计划：每一步改哪个文件、
跑什么测试、退出条件是什么。决策理由、Web 相对客户端的八条劣势、会推翻决策的条件都在 #227，

先决问题要先问业务方，第 6 步只产判断不产功能。**

实施状态（2026-09-20）：第 0 步已拍板（见下），**第 1 步已落地**，数字见
[`00`](00-status.md)。六步分别对应 #229、#232、#231、#228、#233、#230，
Epic #227 的子 issue 表是编号与代价条目的唯一绑定处。

拍板把范围收窄了，后面几步的形状随之变化：

| 拍板项 | 结论（2026-09-20） | 对计划的影响 |
| --- | --- | --- |
| 目标 | 为评审。Web 化的动机是使用体验：更新不必每个用户手动做，代码只维护一处 | 顺序改为 1 → 3 → 6；第 2、5 步推后（rubric 不计分） |

拍板的动机是更新与维护成本。两者都指向同一个结论，但如果哪天只剩后者，客户端加自动更新也能满足它——
这一点记下来，免得以后把结论当成不可动摇的前提。

## 一、决策与边界

三条决策（详见 #227）：全 Web、不做桌面客户端；单租户一客户一实例，不做多租户 SaaS；
两种托管形态共用同一套代码与部署脚本（我方 VM 为默认，客户自有机器为本地形态）。

代价与动作的对应关系，只在这里列一次：

| #227 的代价条目 | 本篇动作 | issue |
| --- | --- | --- |
| 1 上传管道窄于目标量级 | 第 4 步 | #228 |
| 2 数据驻留责任 | 由决策第三条承担，无独立动作 | — |
| 3 算力成本随席位增长 | 第 2 步（护栏）、第 6 步（成本口径） | #232、#230 |
| 4 我方成为全公司单点 | 第 2 步 | #232 |
| 5 开通是多方人工流程 | 第 5 步 | #233 |
| 6 浏览器约束 | 分散在既有 UI 工作，无独立动作 | — |
| 7 隔离在 Web 形态才变成成本 | 第 1 步（声明）、第 6 步（评估） | #229、#230 |
| 8 非模型部分也依赖网络 | 形态固有属性，记录在案 | — |

明确不做：fork dsh；启用 `packages/experimental/`；跨客户多租户；多节点或高可用；对象存储迁移；
自建监控平台；把 Docker 与 compose 请回来；自助注册与开通编排。前两条是硬约束，其余是
「为不存在的规模建设施」。

## 二、实施步骤

顺序是有依赖的，不是优先级排序。第 1 步先做，因为它是唯一「现在就有人能看到别人东西」的一项；
第 3 步必须排在第 1 步之后，因为它需要「会话属于谁」这个事实存在。

### 第 0 步 — 先决问题（已于 2026-09-20 拍板，结论见开头的表）

三个问题的答案在开头的拍板表里，这里只记它们各自解掉了什么：

1. 控制台人数 10 人以内（演示规模）→ 第 6 步维持评估，不实现。
2. 真实体积多数在 10 MB 以内 → 25 MiB 上限当前不是瓶颈，第 4 步只剩「以飞书导入为主路径」
   加一次量级实测；PRD 的 20 万行仍是未确认的建议值（[`08`](08-prd-traceability.md) 第 2 条），
   等真的接近它再谈分片续传。
3. 本期不需要本地部署 → 第 5 步的差异清单推后，第 2 步的备份与清理由我方执行。

**未解**：真实行数尚未确认，所以「10 MB 以内」是当前样本而不是上限承诺；真实月度导出到手后要复测。

### 第 1 步 — 控制台操作员角色门（#229，已落地 2026-09-20）

把共用控制台从「凡登录皆可进」的事实缺口，变成一个被声明的操作员面。设计与三种结局的措辞
边界记在 [`27`](27-login-portal.md)，开启步骤与验证命令在 [`22`](22-lightsail-deploy.md) §9d，
数字与未验项在 [`00`](00-status.md)。落地与原计划的两处出入：

- 判定没有做成门户自己查飞书，而是门户拿自签的用户令牌问后端 `/identity/console-access`，
  后端复用 `access_resolver`。这样角色规则不被复制到门户，代价是多一跳；答案缓存 60 秒、
  失败不缓存。
- 那条路由是唯一不挂 `require_host` 的：门户不持有宿主凭证，理由写在 `api/console.py`。
- 计划里写的「整站扣下 vs 角色门下移」两难基本不成立：`forward_auth` 后面只有 dsh web 一个
  站点，没有另一个只读站会被牵连。原文的顾虑已按此更正。

改哪里：`portal/src/portal_app/main.py` 的 `/verify` 增加角色判定；`pages.py` 区分「未登录」
与「无控制台授权」两种 401 卡片（沿用 `docs/design/12-states.html` 的通告形态）；
`data/mappings/access-control.example.yaml` 补一个控制台操作员角色；判定复用
`access_resolver` 与其既有缓存，不新写名单。

飞书不可达时扣下整站（2026-09-20 拍板）。当初担心的「连只读页面都进不去」不成立：
`forward_auth` 后面只有 dsh web 一个站点，四部门浏览页也在这个 shell 里。被否的备选是
「`forward_auth` 只做登录判定、角色门下移到应用内路由」——故障面更小，但判定会散在多处。

测试：portal 与 backend 各自翻转；覆盖无角色、角色缺失、飞书不可达三条路径。措辞不得出现
「你没有权限」这类越界断言（扣下不等于拒绝）。

退出条件：未声明操作员角色的已登录员工到不了控制台，且看到的是准确措辞；演示脚本里的账号
已随之调整；[`27`](27-login-portal.md) 与 [`22`](22-lightsail-deploy.md) §7/§9c 同步；
产品文档写明控制台是共用的、同时在里面的人互相可见。

### 第 2 步 — 运维底线（#232）

Web 形态把「全公司单点」和「模型账单」一起接了过来，这一步把 [`22`](22-lightsail-deploy.md) §11
里的已知坑变成交付前必须关闭的项。

七项：备份与一次恢复演练（含两份 gitignored 的人工配置——它们是客户资产且只存在于实例上）；
保留策略（含当前未定的孤儿 blob）；清理脚本进 systemd timer 并留执行记录；模型 key 的平台侧硬上限
加本地用量计量；`--trusted-host` 两种匹配形态实测；每个密钥的轮换手册（步骤、影响面、验证命令）；
重启空窗要么写进 SLA 要么给最小改动。

改哪里：`deploy/` 下新增 timer 与备份脚本；`deploy/preflight.sh` 加可机器检查的部分；
[`22`](22-lightsail-deploy.md) 新增运维小节并把已被实测替代的猜测删掉。

退出条件：每项都有验证命令且通过，恢复演练的耗时与丢失窗口进 [`00`](00-status.md)。

### 第 3 步 — 模型发起读取的可归因身份（#231，已落地 2026-09-20）

落地形态与计划推荐的「会话绑定身份」同向但不同：浏览器交出**自己的门户令牌**，宿主验签一次后
在模型触发的读取上原样转发，后端逐请求验签——不是宿主断言一个名字。边界与两条限制记在
[`27`](27-login-portal.md) 末节，数字与未验项在 [`00`](00-status.md)。与计划的三处出入：

- 计划假设第 1 步会提供「会话属于谁」这个事实。它没有：#229 只保证进得来的人是被声明的操作员。
  真正的绑定事实由本步自己建（浏览器 `POST /bridgeflow/actor`）。
- 工具的 `exec` 没有会话 id，所以模型触发的调用无法说自己属于哪个会话。于是规则是「只有一个人
  绑定时才归属，两个人同时绑定就什么都不挂」——有歧义等于没有。
- 计划里的需求 2「缺席就是缺席、不得默认放行」只做到一半：缺席时**归属**缺席，但读取仍然执行。
  把它改成拒绝是另一次拍板，见下节风险第 7 条。

让 `BRIDGEFLOW_SERVICE_TOKEN` 退回传输凭证的位置，不再充当身份。当前模型发起的工具读取没有
浏览器、也就没有 `x-bridgeflow-user`，身份即「可信主机」；后果是可归因性，不是越权入口
（工具集已由 `dsh/no-shell.patch.yml` 在 profile 层收窄）。

推荐形态是会话绑定身份：会话建立时记录归属，模型发起的调用带上该会话的人。所以它依赖第 1 步
提供「这个会话属于谁」。透传门户 JWT 的方案要先解决 15 分钟有效期与异步长任务的矛盾，而
「发起时授权、执行中不复验」与既有的执行前撤权检查冲突。

改哪里：宿主侧调用点（`plugins/src/backend.ts`、`plugins/src/web.ts`、`approval/answerer.ts`）；
后端对「主机凭证有效但身份缺席」的明确行为（不得默认放行）；审计字段补人。回执签名
（`approval/receipts.ts`）的 HMAC 输入若变动，必须同步测试，避免默默让旧回执不可验。

退出条件：审计能回答「哪个人的哪次请求触发了这次读取」；身份缺席与范围不符两条拒绝路径有测试；
[`27`](27-login-portal.md) 与 [`16`](16-dsh-web-review.md) 的表述从「不宣称」改为实际做到了什么。

### 第 4 步 — 上传主路径与量级实测（#228）

先做实测再改上限。`bridgeflow_max_upload_bytes` 是一道防御，同时挡内存放大与拒服务面，
简单调大等于把防御删掉。

三个候选：以飞书导入为主路径（[`32`](32-feishu-sheets-bitable-read.md)、[`33`](33-feishu-sheets-bitable-impl.md)
已有服务器侧流式分页，浏览器上传上限不动）；分片加续传；提高上限配合流式解析。第一个是推荐起点，
但要同时回答「非飞书客户怎么导入」，否则等于把第二个推给未来某个客户。

退出条件：目标量级下导入要么成功要么明确报错，不允许静默截断；失败可归因（沿用
`x-bridgeflow-reason` 约定）；内存与行数的关系有实测曲线并进 [`00`](00-status.md)。
本步只管导入路径，不承诺端到端十分钟（[`11`](11-proposal-review.md) 已记当前规模差数个量级）。

### 第 5 步 — 开通手册与配置下发（#233）

开通流程本身就是产品的一部分：目标客户没有数据团队（[`01`](01-problem-and-hmw.md)），
而开通要走完实例、域名与证书、客户侧飞书管理员的两步、两份人工配置、密钥、逐条验收。

产出：按角色分栏的开通清单（我方做什么、客户飞书管理员做什么、客户业务方要提供什么），每步带
验证命令或验证现象；`scripts/feishu_membership_check.py` 纳入 preflight；两份人工配置的交付
固定走 §5b 的 `config-put.sh`，不再 SSH 手改、不另开通道；本地部署形态的差异清单
（无公网域名怎么办证书、我方无 SSH 时谁执行第 2 步的备份与清理、升级怎么送达）；升级与回滚章节
（`data/uploads|outputs`、`plugins/dist`、两份配置全靠 gitignore 存活，绝不 `git clean`）。

手册要写清两条容易卡死开通的事实：通讯录权限申请不下来时可只走 wiki 一条路（#204 已有结论）；
群组或部门型成员不会被展开，授权以人直接加进知识库为准（[`27`](27-login-portal.md)）。

退出条件：一个新客户能按手册走通，且手册里没有任何密钥值。

### 第 6 步 — 按人隔离工作区的评估（#230）

这一步产出判断，不产功能，且结论可能是「不做」。

`dsh` 是单操作员运行时，而不 fork、不用 experimental 是硬约束，所以合法做法只剩一人一个
dsh 进程（按门户 `sub` 路由、各自 `DSH_HOME`）。它的代价是内存，按席位计，所以这个障碍的本质是
经济性而非技术性。要回答六问：进程模型（常驻还是按需加空闲回收）、路由归属、按人取 launch token、
N 份 `DSH_HOME` 对备份与清理的影响、审批队列语义（跨部门批准怎么到达批准人，这一条最可能推翻朴素设计）、
每并发席位的成本口径。

退出条件：六问有结论、含被否决方案与理由；单个运行时的内存与冷启动数字进 [`00`](00-status.md)；
[`13`](13-golden-standard.md) 补一句「dsh 无内建多用户归属」的能力边界事实。不得以「采用了某个
设计模式」为由标记完成（沿用 [`23`](23-extension-contracts.md) 的口径）。

## 四、风险与待拍板

1. 第 1 步的飞书不可达时是否扣下整站，两个方案各有故障面，需拍板。
2. 第 3 步与第 1 步的顺序依赖不可交换；先做第 3 步会得到一个没有可靠身份可绑的实现。
3. 第 4 步的验收阈值取决于第 0 步的第 2 问；问题没答案就先不动手。
4. 本地部署形态下第 2 步由谁执行，是决策第三条唯一没闭合的地方（我方无 SSH、无日志）。
5. 第 6 步的审批队列语义可能要求「按人隔离会话」与「共享审批队列」并存，会让设计明显复杂化。
6. 本篇是部署形态的落地计划，不回答「可以卖了吗」。真实飞书角色端到端、字段字典与公司谈定、
   真实导出上的模型质量评测三项缺证据，结论仍是先一个 design partner 试点，不是 GA。
7. **待拍板（第 3 步留下的）**：模型读取缺少归属时，是照读还是拒绝。现状是照读——归属缺席、
   读取执行，审计如实记成 `host`。改成拒绝会让无人值守运行与超过 15 分钟的运行在令牌过期后停住，
   这与「执行前撤权检查」的既有约定同向，但会牵动演示。两人同时绑定时归属为空，也在这条里一起定：
   是退化为无归属（现状），还是干脆拒绝。
